title: Course contract compiler
---

I don’t think Rust is over-engineering **if the thing you’re building is really a contract compiler/publisher**, rather than merely an Astro lint rule.

The important architectural decision is that **Astro should not be the source of truth for the worker contract**. Your Rust workers already own that contract.

I’d make the boundary look like this:

```text
Rust worker definitions
        │
        │ serde + schemars
        ▼
worker contract / manifest
        │
        ├── worker name
        ├── worker version
        ├── config JSON Schema
        ├── allowed frontend components
        ├── component prop schemas
        └── compatibility/version information
                  │
             ┌────┴─────┐
             ▼          ▼
       Astro/dev      publisher
       validation     / compiler
```

### Make Rust the contract authority

Suppose the backend has:

```rust
#[derive(
    Serialize,
    Deserialize,
    JsonSchema,
)]
#[serde(deny_unknown_fields)]
pub struct ImageWorkerConfig {
    pub width: u32,
    pub height: u32,
    pub format: ImageFormat,
    pub quality: Option<u8>,
}
```

With `schemars`, the same Rust types can generate JSON Schema. Schemars is specifically designed to derive JSON Schema while respecting Serde attributes such as renames and `deny_unknown_fields`. ([Docs.rs][1])

Then your worker release could emit something like:

```json
{
  "worker": "image",
  "version": "3.2.0",

  "components": {
    "ImageWorker": {
      "config": {
        "$ref": "#/$defs/ImageWorkerConfig"
      }
    }
  },

  "$defs": {
    "ImageWorkerConfig": {
      "...": "generated by schemars"
    }
  }
}
```

Now **neither Astro nor your compiler needs to understand the Rust source code**. They consume a stable contract artifact.

That distinction is valuable.

---

## Where I would _not_ use Astro's built-in schema system

Astro Content Collections are very good for page-level data:

```yaml
---
title: Foo
description: Bar
draft: false
---
```

Astro's Zod support gives you validation and TypeScript inference, and custom Content Loaders can even provide schemas dynamically. ([Astro Documentation][2])

So I would happily let Astro handle things like:

```ts
const pageSchema = z.object({
  title: z.string(),
  description: z.string().optional(),
  worker: z.string(),
  workerVersion: z.string(),
});
```

But your real requirement sounds more like:

```mdx
---
worker: image
workerVersion: 3.2.0
---

<ImageWorker width={1200} height={800} format="webp" />
```

and you want to verify:

```text
Does worker "image" exist?

Does version 3.2.0 exist?

Does <ImageWorker> exist in that version?

Is "format" valid?

Did v3.2 rename "quality" to "compression"?

Is width required?

Is this particular combination of parameters allowed?

Can this document actually be published against that worker?
```

That's substantially beyond what I would try to express through Astro Content Collections.

At that point you have a **domain compiler**.

---

## I would probably write that compiler in Rust

Especially because you mentioned eventual publishing.

Not because Rust parses MDX dramatically better than TypeScript. TypeScript could handle this perfectly well.

The advantage is **ownership of your domain model**.

You could have a workspace like:

```text
workspace/
├── worker-contract/
│   ├── WorkerDefinition
│   ├── WorkerVersion
│   ├── schemas
│   └── validation rules
│
├── worker-image/
├── worker-video/
│
└── content-compiler/
    ├── mdx parser
    ├── frontend validator
    ├── diagnostics
    ├── artifact builder
    └── publish
```

And:

```rust
worker-contract
       ↑
       │
 ┌─────┴──────────┐
 │                │
worker runtime    content compiler
```

That's a nice property: your backend and content compiler can literally depend on the **same Rust contract crate**.

There is no "Rust schema → TS schema → validator → hopefully identical behavior" gap.

---

## But I would still integrate it into Astro

This is where I think the hybrid architecture wins.

Don't reimplement Astro.

Have:

```text
Astro
  │
  │ invokes
  ▼
my-content-compiler check ./content/foo.mdx
```

Initially, even this is enough:

```ts
import { execFile } from "node:child_process";
```

inside an Astro integration/Vite plugin.

Astro integrations have lifecycle hooks specifically for adding build/dev functionality and Vite plugins. ([Astro Documentation][3])

So during:

```text
astro dev
```

you could get:

```text
src/content/foo.mdx:18:5

18 | <ImageWorker format="png" compression={92} />
                         ^^^^^^^^^^^

Worker image@2.4.0 does not support prop `compression`.
`compression` was introduced in image@3.0.0.
```

And:

```text
astro build
```

fails if the compiler reports an error.

Later you could replace the subprocess boundary with `napi-rs` if startup/IPC becomes noticeable.

I **wouldn't start with N-API bindings**, though. A CLI boundary is dramatically simpler and forces your compiler to remain independent of Astro.

That's useful if eventually you want:

```bash
mycompiler check .
mycompiler build .
mycompiler publish .
```

rather than:

```bash
astro build
```

being the only way it can operate.

# The most important thing I'd design now

Don't directly validate JSX against Rust structs.

Create a **versioned contract representation**.

For example:

```rust
pub struct WorkerContract {
    pub worker: WorkerId,
    pub version: Version,
    pub components: Vec<ComponentContract>,
}

pub struct ComponentContract {
    pub name: String,
    pub props: JsonSchema,
}
```

The actual Rust worker might say:

```rust
#[derive(JsonSchema)]
struct ResizeConfig {
    width: u32,
    height: Option<u32>,
    fit: Fit,
}
```

and your released contract becomes:

```text
image@1.0
    Image
        width: integer required
        height: integer optional
        fit: cover | contain

image@2.0
    Image
        width: integer required
        height: integer optional
        fit: cover | contain | crop
        quality: integer optional
```

Your compiler doesn't care where that schema came from.

That means later worker contracts could theoretically come from:

```text
Rust
OpenAPI
Protobuf
remote registry
generated code
another language
```

without changing the MDX compiler.

---

## JSON Schema fits this extremely well

I would probably choose it as the interchange format.

On the worker side:

```rust
serde
+
schemars
```

Schemars currently generates JSON Schema 2020-12 by default and derives directly from Rust types. ([Docs.rs][4])

On your Rust compiler side, the `jsonschema` crate can compile and validate those schemas and produces structured error locations. The current crate also supports Draft 2020-12. ([Docs.rs][5])

So:

```rust
let validator =
    jsonschema::validator_for(&worker_schema)?;

for error in validator.iter_errors(&props) {
    diagnostics.push(...);
}
```

That's better than hand-writing:

```rust
if component == "Foo" {
    if props.contains("x") ...
}
```

for every worker.

## There's one significant MDX problem to decide early

Consider:

```mdx
<ImageWorker width={1200} />
```

Easy.

Your compiler can turn that into:

```json
{
  "width": 1200
}
```

and JSON-Schema validate it.

But:

```mdx
<ImageWorker width={frontmatter.imageWidth} />
```

is different.

And:

```mdx
<ImageWorker width={calculateWidth(foo)} />
```

is much harder.

The MDX parser/OXC can tell you:

> This is a valid JavaScript expression.

It cannot necessarily tell you:

> This expression evaluates to a `u32` acceptable by worker image@3.2.

You'd need type/scope analysis and potentially execution.

I would **avoid building a TypeScript compiler inside your compiler**.

Instead, define which worker-facing attributes must be statically evaluable.

For example, permit:

```mdx
<Foo value="hello" />
<Foo value={123} />
<Foo value={true} />
<Foo value={["a", "b"]} />
<Foo value={{ width: 100 }} />
```

possibly:

```mdx
<Foo value={frontmatter.foo} />
```

if you can resolve it.

But reject:

```mdx
<Foo value={getFoo()} />
<Foo value={x + y} />
<Foo value={await fetch(...)} />
```

for contract-bearing configuration.

That turns your compiler into something deterministic:

```text
MDX
 ↓
AST
 ↓
extract component
 ↓
constant evaluation
 ↓
serde_json::Value
 ↓
JSON Schema validation
```

This is **much simpler** than TypeScript type checking and probably much safer for publishing too.

## And your TOML fits naturally

Since your workers already have TOML configuration, Rust is especially convenient.

The current `toml` crate directly supports Serde deserialization. ([Docs.rs][6])

So the exact same type:

```rust
#[derive(
    Deserialize,
    JsonSchema,
)]
struct WorkerConfig {
    endpoint: String,
    timeout: u64,
}
```

can provide:

```text
worker.toml
    ↓
Deserialize<WorkerConfig>
```

and:

```text
WorkerConfig
    ↓
JsonSchema
    ↓
frontend contract
```

That's a strong argument for keeping the contract layer in Rust.

---

## So: are you over-engineering?

If your requirement were only:

> Make sure MDX frontmatter has `title`, `worker`, and `version`.

Then yes. Use Astro + Zod and be done.

If it were:

> Check that `<Worker>` has known props.

I'd probably still write it in TypeScript as an MDX/Astro plugin.

But your actual direction sounds like:

```text
versioned Rust workers
       +
versioned TOML definitions
       +
frontend component contracts
       +
cross-version compatibility
       +
good source diagnostics
       +
build validation
       +
eventual packaging/publishing
```

At that point **a standalone Rust compiler is quite reasonable**.

What I would avoid is making it an actual _Astro compiler_. Make it a small domain compiler that happens to consume MDX and has an Astro integration.

The split I'd choose is:

```text
                 RUST

       worker-contract crate
              │
      ┌───────┴────────┐
      ▼                ▼
 worker runtime   content compiler
                       │
               parse / validate
                       │
               build / publish
                       │
                       ▼
              compiled artifact


              TYPESCRIPT

               Astro integration
                       │
                invokes compiler
                       │
              surfaces diagnostics
```

That gives you the best part of both approaches: **Astro keeps doing Astro things; Rust owns worker correctness and publishing semantics.**

And I think the particularly valuable design decision is **`schemars`-generated versioned JSON Schema as the boundary**, not whether the first MDX parser happens to be Rust or TypeScript. ([Docs.rs][4])
